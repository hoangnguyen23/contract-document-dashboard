## Exact command source and SoD

START_REVIEW reason: independent current scoped DATA_OFFICER OPEN→IN_REVIEW. REJECT reason: invalid request→REJECTED, immutable reason/history. DECIDE decision,basis,reason,manifest: IN_REVIEW→DECIDED with ALLOW/PARTIAL exact nonnull actionable manifest; DEFER/REFUSE manifest null and no EXECUTE. Independent officer excludes original requester and actual stable source/copy contributors. Never accept role DATA_OFFICER as implicit sensitive-read grant. The officer who decided may execute if still scoped/eligible and not requester; do not require an invented separate executor.

EXECUTE manifestVersion,manifestHash,reason: exact approved manifest only; enqueue durable intent+Job(DATA_DISPOSITION,parent DATA_REQUEST) and audit/idempotency atomically, request stays DECIDED. Only all exact record effects and actual byte cleanup success make EXECUTED. Failure stays DECIDED with FAILED Job; no empty success, no swallowing IO errors.

PLACE_HOLD recordIds,reason,basisFileIds(1..20): scoped DATA_OFFICER with exact source evidence, immutable hold event; records within authorized request/source scope, never guess arbitrary target. RELEASE_HOLD holdId,reason,basisFileIds: scoped independent officer different from placedBy, excluding requester/self-review; immutable release event. No rewriting old placement evidence/reason. LegalHold projection exact id,recordIds,reason,basisFileIds,placedBy,placedAt,releasedBy(nullable),releasedAt(nullable). Holds/holdIds max100; reject overflow rather than truncate history. Hold applies to target records globally across requests; request-local holdIds alone cannot enforce it. Current all active record holds must be checked even if manifest.holdId is null or points to a released/different hold.

## Holds, reservations, durable bytes and recovery

Use deterministic record identity locks shared by PLACE_HOLD, EXECUTE reservation, worker, correction and file delete/scan/attachment source paths; a DataRequest row lock alone does not protect records shared by two requests. Acquire authoritative ancestors first in deterministic order across selected Contracts/Relationships, then sorted target locks, request/hold/intents/jobs consistently; reconcile actual existing lock hierarchy, do not invent leaf→parent inversions. Recheck current users/scope/supplemental grants both before idempotency and under TX. Read-only hints never reserve, mutate file associations or assess evidence.

Hold before committed disposition reservation:409 HOLD_ACTIVE and no effect. Reservation committed first: later hold409 DISPOSITION_COMMITTED, including FAILED/incomplete cleanup; never promise hold can undo irreversible committed intent. Durable intent exact record/version/action/source/replacement hashes, reservation and immutable manifest/decision must survive crash. An intent/reservation cannot be discarded just because IO failed or a new actor replays a different key. Scope/revocation/holds/current metadata checked again in worker before new side effects. Recovery of already authorized irreversible intent needs precise distinction from fresh authorization and must not rewrite committed source.

DB+byte deletion is not one atomic transaction. Recommended small per-record durable phases: validate/freeze/reserve in DB; files-owned commit logical disposition and exact cleanup keys under shared blob-reference guards; actual guarded deletion outside enclosing DB row TX; durable cleanup-complete acknowledgement; only then overall Job SUCCEEDED/request EXECUTED. Persist original pending cleanup key/hash in a restricted intent row until success; DB rollback after filesystem deletion must not restore apparently live bytes. Retry reconciles completed effects and exact keys, never reruns fresh metadata mutation or deletes regenerated/shared content. If using blob pointer removal before physical deletion, durable cleanup intent must prevent orphan maintenance silently completing/reporting success or erasing proof; table/guard coordination required. Do not execute filesystem deletion from an ordinary afterCommit callback with swallowed exception and then mark job successful.

Concrete baseline trap: PrivateBlobStore.delete(key) returns normally when cg_file_blob still references key; it is designed for unreferenced orphan cleanup, not an assertion that requested disposition deleted bytes. It also uses REQUIRES_NEW/table reference lock; calling it inside a TX holding conflicting blob rows can block/fail. Provide a files-owned explicit disposition-cleanup outcome/reconciliation path, respecting cross-process .guards and both storage_key/redacted_storage_key reference columns. File cloning may share exact key: source bytes required by another retained record cannot be physically deleted and called successful erasure. Either authorized finite scope includes all required byte owners or refuse/defer with actual basis; do not silently remove only one logical pointer and promise global byte erasure. Cleanup IO failure must propagate FAILED/incomplete. New hold after reservation still returns committed409.

Use existing JobQueue lease60s/renew20s, bounded worker, fencing owner/attempt, requeue expired lease, max5 exponential capped15min and manual retry audited reset. Stable DATA_DISPOSITION dedupeKey+manifestVersion/hash, expected source version and correlation; no extra public job kind. DataRequest version changes on enqueue/hold/history may be expected, so do not incorrectly compare raw mutable aggregate version to the pre-enqueue value while ignoring exact decision/source semantics. Same record effects once across retry/crash, no invented exactly-once external guarantee. JobService authorization/project/retry must call real privacy-owned current-source guards and keep exact reserved intent, not generic MAKER/CHECKER fallback.
