# Private evidence and scan jobs

Implemented HTTP operations: `listFiles`, `uploadFile`, `getFile`, `deleteUnattachedFile`, `commandFile` (RETRY), `downloadFile`, `listJobs`, `getJob`, `commandJob` (FILE_SCAN retries). Other job kinds retain explicit unavailable retry behavior until their real workers exist.

Multipart upload validates the exact canonical closed `FileUpload` shape, rejects unknown/repeated parts, derives MIME from bytes, enforces 10 MiB per file and 20 files/100 MiB per parent staging budget. Upload requires an existing authorized parent. A private opaque blob key and server SHA-256 are finalized before the transaction creates metadata, audit and a durable FILE_SCAN intent. There are no public storage URLs. `CG_STORAGE_ROOT`, `CG_SCANNER_HOST` and `CG_SCANNER_PORT` configure the actual adapters.

ClamAV uses the real clamd VERSION/INSTREAM socket protocol with bounded connection/read/whole-command deadlines, two scan slots and 20-second lease renewal. External scan work runs outside the domain transaction. Completion locks parent then file, rechecks current authorization/state/source version/hash, verifies lease ownership and updates file+audit+job atomically. Outages remain quarantined during at most five bounded backoff attempts and finish SCAN_FAILED; fifth expired crash leases are reconciled to SCAN_FAILED. No outage or synthetic fixture marks a live file CLEAN. Human verification remains NOT_CHECKED after scanning.

Private metadata/content/job authorization inherits the actual parent. Sensitive full downloads require SENSITIVE_READ; auditor compound roles do not bypass actual assignment. REDACTED requires an independently verified private replacement record and returns READINESS_BLOCKED when absent, with no original fallback. Returned hash and length describe the returned bytes. Redaction/disposition production APIs are future G5 work, so this module does not fabricate replacement files.

PUT draft references require CLEAN same-parent/same-branch files and preserve historical associations. Own unattached uploads can be deleted; internal deletion authorization tombstones preserve authenticated/scoped cached 204 replay. Bytes are removed only after commit and only when neither original nor redacted reference points at the private key. A failed physical cleanup safely leaves an unreferenced blob for maintenance, rather than corrupting referenced history. Complete coherent DB/blob backup/restore remains operational follow-up work.

`BlobMaintenance` reconciles unreferenced finalized UUID blobs and recognized quarantine `.part` files only after a 24-hour grace period measured against the real application Clock. It enumerates the verified private root without descending into directories, never follows symlinks and leaves arbitrary/unrecognized files alone. Each pass examines at most 512 entries/32 old candidates with a two-second processing budget; a retained directory cursor continues subsequent passes so a prefix of referenced files cannot starve later orphans. The initial delay is 60 seconds and interval five minutes; `cg.storage-maintenance.initial-delay-ms`, `interval-ms`, `scan-limit` and `candidate-limit` configure the bounded worker.

New blob writes hold an exclusive OS lock in a separate fixed `.guards/<opaque-key>.lck` sidecar through HTTP request completion or transaction completion. Original bytes themselves are not locked, so Windows scanner/download reads through another handle remain possible. A crash releases the OS lock. The maintenance worker obtains the same sidecar non-blockingly and skips active upload lifecycles even when a stalled request outlives the 24-hour grace period. Before unlinking it opens a short independent transaction, obtains `cg_file_blob` SHARE ROW EXCLUSIVE with a 250 ms lock timeout, and checks both `storage_key` and `redacted_storage_key`; this serializes reference INSERT/UPDATE/DELETE across all JVMs. Clone source bytes remain protected by their existing database reference and source aggregate/file lock until the new reference commits. A database reference preserves bytes even when its File entity is missing. Candidate root/file identity, regular-file kind and unchanged age are rechecked immediately before deletion; storage changes fail closed. Sidecar lock files are retained as small coordination tombstones to avoid replacing a lock inode while another process has opened it, and are not traversed by maintenance.

`ManagedFileIdentity` handles the documented optional nature of Java `BasicFileAttributes.fileKey`: non-Windows providers must expose a non-null key; Windows uses the official pinned `jna-platform`/transitive `jna` 5.19.1 mapping. It opens metadata-only `OPEN_EXISTING` handles with `OPEN_REPARSE_POINT`/`BACKUP_SEMANTICS`, rejects reparse points and mismatched disk/file kinds from the handle, and binds each identity to the volume serial plus 128-bit FileIdInfo. Handles always close in `finally`; unsupported identity lookup fails closed, without path/mtime or null-equality fallback. The same identity implementation protects root/guard directories, download byte identity and maintenance candidates. The Windows Java 25 classpath launcher should use `--enable-native-access=ALL-UNNAMED` explicitly. Sources: [Microsoft FileIdInfo](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info), [JNA 5.19.1 mappings](https://github.com/java-native-access/jna/tree/5.19.1/contrib/platform/src/com/sun/jna/platform/win32), [Oracle native access](https://docs.oracle.com/en/java/javase/25/core/restricted-methods.html).

Future artifact workers outside an HTTP request use `try (var pending = blobs.writePending(input))` and retain `pending` until their reference transaction has committed or rolled back; `pending.stored()` supplies immutable metadata. The `write` convenience API requires a request or active transaction lifecycle, rather than releasing an upload guard before reference creation. No new HTTP operation, caller-provided path or public deletion endpoint was added. Immediate cleanup also rechecks both reference columns under the same database guard. Maintenance and lifecycle-release failures log sanitized messages/counts without storage paths/content or exceptions; they leave bytes for later reconciliation and do not rewrite cached success/replay responses.

Job wire snapshots/version/timestamps are maintained by SQL triggers from the durable queue. Retry checks current ownership/scope before cache replay and new-effect state/source guards afterwards. Semantic trigger version changes exclude lease heartbeat updates.

No tests, HTTP acceptance calls or runtime file-deletion scenarios were run. The module is compiled/packaged with `mvnw.cmd '-Dmaven.test.skip=true' package`; runtime/scanner/browser/maintenance/recovery acceptance remains pending.
